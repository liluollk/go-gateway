## 1. 日志轮转时重复加锁导致死锁

### 实际场景

网关从早上一直运行到第二天凌晨。日志文件每天一个：

```text
gateway-2026-07-27.log
gateway-2026-07-28.log
```

凌晨 00:00 后，第一条请求到达，日志组件发现日期变化，于是尝试关闭旧日志并打开新日志。此时请求一直不返回，后续请求也可能逐渐堆积。

### 问题代码

```go
type Logger struct {
    mu sync.Mutex
}

func (l *Logger) Write(entry *LogEntry) {
    l.mu.Lock()
    defer l.mu.Unlock()

    if dateChanged() {
        l.rotate() // 已经持有 mu 的情况下调用
    }
}

func (l *Logger) rotate() {
    l.mu.Lock() // 再次加同一把锁
    defer l.mu.Unlock()
    // 切换日志文件
}
```

### 为什么会死锁

`sync.Mutex` 不是可重入锁。同一个执行流程已经持有 `mu` 后，再次执行 `Lock()` 会一直等待解锁；但解锁语句在外层 `Write()` 结束时才会执行，因此形成了“自己等待自己”的循环。

```text
Write 加锁
  └─ rotate 再次加锁
       └─ 等待 Write 解锁
            └─ Write 等待 rotate 返回
```

### 修复代码

将真正执行轮转的逻辑拆成 `rotateLocked()`。它约定：**调用者已经持有锁，函数内部不能再次加锁**。

```go
func (l *Logger) rotate() error {
    l.mu.Lock()
    defer l.mu.Unlock()
    return l.rotateLocked()
}

func (l *Logger) rotateLocked() error {
    // 这里不再 Lock，因为调用者已经持有锁
    if l.file != nil {
        _ = l.file.Close()
    }

    file, err := os.OpenFile(filename(),
        os.O_APPEND|os.O_CREATE|os.O_WRONLY, 0644)
    if err != nil {
        return err
    }
    l.file = file
    l.encoder = json.NewEncoder(file)
    return nil
}

func (l *Logger) Write(entry *LogEntry) {
    l.mu.Lock()
    defer l.mu.Unlock()

    if dateChanged() {
        _ = l.rotateLocked() // 不重复加锁
    }
    _ = l.encoder.Encode(entry)
}
```

### 验证方式

```bash
go test ./...
go vet ./...
go build ./...
```

还应进行跨日期测试：让测试替换日期判断，模拟从 `2026-07-27` 切换到 `2026-07-28`，确认写日志可以返回而不是卡住。

### 学到的知识

- 加锁后调用其他方法时，要确认被调用方法是否也会加同一把锁。
- 可以使用 `xxxLocked()` 作为命名约定，表示“调用前必须已经持锁”。
- 锁的范围应尽量小，但关闭旧文件、切换 encoder、写入日志需要保持原子性。

## 2. 流式响应缓存响应体导致内存持续增长

### 实际场景

用户使用流式聊天：

```json
{
  "model": "gpt-4o",
  "messages": [{"role":"user","content":"请写一篇长文章"}],
  "stream": true
}
```

上游每隔一小段时间返回一个 SSE 数据块。一次回答可能持续几分钟，很多用户同时使用时，网关内存持续上升。

### 问题代码

```go
type responseWriter struct {
    http.ResponseWriter
    body bytes.Buffer
}

func (rw *responseWriter) Write(data []byte) (int, error) {
    rw.body.Write(data)             // 保存一份无用副本
    return rw.ResponseWriter.Write(data) // 再发给客户端
}
```

假设每个流式请求返回 10 MB，同时有 100 个请求：

```text
10 MB × 100 个请求 = 约 1 GB 额外缓存
```

而日志中间件实际上只需要状态码，不需要完整响应体。

### 修复代码

```go
type responseWriter struct {
    http.ResponseWriter
    statusCode int
}

func (rw *responseWriter) WriteHeader(code int) {
    rw.statusCode = code
    rw.ResponseWriter.WriteHeader(code)
}

// 不再重写 Write，直接使用嵌入的 ResponseWriter 转发数据
```

### 验证方式

可以运行并发测试，然后观察进程内存：

```bash
go test ./... -count=1
go test -race ./...
```

重点检查：流式响应发送过程中，内存不会随着已发送数据无限增长。

### 学到的知识

- 流式响应不是一次性返回，任何请求级缓存都可能随着连接时间变大。
- 如果数据没有消费者，就不要保存。
- `http.ResponseWriter` 包装器只实现真正需要拦截的方法，例如记录状态码时只需要重写 `WriteHeader`。
- 设计长连接功能时，要特别关注“每个连接占用多少内存”。

## 3. 把上游错误原样返回给客户端导致信息泄露

### 实际场景

供应商返回 502，并带有内部错误：

```text
connect to 10.12.3.8:443: i/o timeout; upstream cluster=provider-a-prod
```

如果网关直接把这段内容返回给业务方，客户端就能看到供应商的内部地址和部署信息。

### 问题代码

```go
body, _ := io.ReadAll(upstreamResp.Body)

errors.NewProviderError(
    fmt.Sprintf("upstream status %d: %s", upstreamResp.StatusCode, body),
).ToHTTP(w, http.StatusBadGateway)
```

### 为什么不安全

上游错误可能包含：

- 内部 IP、域名和服务名称
- 供应商请求 ID 和内部路径
- 数据库或代理错误
- 不应暴露的调试信息

而且供应商错误格式不稳定，客户端会被迫处理不同厂商的原始错误。

### 修复代码

详细信息写入网关日志，返回统一的外部错误：

```go
body, _ := io.ReadAll(upstreamResp.Body)
log.Printf("upstream error: status=%d body=%s",
    upstreamResp.StatusCode, string(body))

errors.NewProviderError("upstream service error").ToHTTP(
    w, http.StatusBadGateway,
)
```

客户端得到稳定格式：

```json
{
  "error": {
    "code": "PROVIDER_ERROR",
    "message": "Provider error: upstream service error"
  }
}
```

### 验证方式

使用一个模拟上游返回内部信息：

```go
upstream.WriteHeader(http.StatusBadGateway)
fmt.Fprint(upstream, "internal IP: 10.12.3.8")
```

断言网关响应中不包含 `10.12.3.8`，但日志中仍然有足够的排障信息。

### 学到的知识

- **对外错误**和**内部诊断日志**应该分离。
- API 错误格式要稳定，不能把供应商协议直接泄露给客户端。
- 日志也要注意访问权限，详细错误不应被所有业务用户读取。

## 4. 配置文件和日志文件没有加入 Git 忽略清单

### 实际场景

开发者本地修改 `config.yaml`，把真实供应商密钥直接写进去：

```yaml
api_key: sk-real-production-key
```

随后执行：

```bash
git add .
git commit -m "update config"
git push
```

密钥就进入了远程仓库和 Git 历史。

另一个常见情况是，每次启动网关都会产生新的日志文件，导致 Git 状态出现大量无关变更。

### 推荐文件划分

```text
config.example.yaml  # 提交：只放模板和 ${ENV_VAR}
config.yaml          # 不提交：本地真实配置
.env.example         # 提交：环境变量名称示例
.env                 # 不提交：本地真实密钥
logs/                # 不提交：运行时日志
test_logs/           # 不提交：测试日志
```

### 修复代码

`.gitignore` 中加入：

```gitignore
config.yaml
.env
logs/
test_logs/
```

配置中只引用环境变量：

```yaml
providers:
  - id: openai-main
    api_key: ${OPENAI_API_KEY} # 密钥从环境变量读取
```

### 验证方式

```bash
git status --short
```

在 `config.yaml` 写入本地测试内容后，它不应出现在待提交列表中。

如果密钥曾经提交过，**仅删除文件是不够的**，还应立即轮换密钥，并清理 Git 历史。

### 学到的知识

- `.gitignore` 只能防止“以后被加入”，不能删除已经提交的历史。
- 真实密钥应使用环境变量、密钥管理服务或部署平台 Secret。
- 日志是运行时产物，不应该和源代码一起提交。

## 5. 配置环境变量名称与测试不一致

### 实际场景

配置文件使用：

```yaml
api_key: ${OPENAI_API_KEY}
```

但测试只设置了：

```go
os.Setenv("TEST_API_KEY", "sk-test")
```

结果配置加载失败，因为程序真正需要的是 `OPENAI_API_KEY`。

### 根因

环境变量替换是按名称精确匹配的：

```text
配置需要 OPENAI_API_KEY
测试提供 TEST_API_KEY
两者不是同一个变量
```

### 正确测试方式

```go
func TestLoad_ValidConfig(t *testing.T) {
    t.Setenv("OPENAI_API_KEY", "sk-test-openai")
    t.Setenv("ANTHROPIC_API_KEY", "sk-test-anthropic")

    cfg, err := Load("../../config.yaml")
    if err != nil {
        t.Fatalf("load config: %v", err)
    }
    if cfg.Server.WriteTimeout != 300*time.Second {
        t.Fatalf("expected 300s write timeout")
    }
}
```

`t.Setenv` 会在测试结束后自动恢复环境变量，比手动 `Setenv` + `defer Unsetenv` 更不容易忘记清理。

### 验证方式

配置模块至少应覆盖：

```bash
go test ./internal/config/ -v
```

应测试：

- 正常配置
- 配置文件不存在
- 环境变量未设置
- provider 类型非法
- route 引用了不存在的 provider
- provider 不支持 route 中的模型

### 学到的知识

- 配置中的环境变量名称是接口契约的一部分。
- 测试环境必须模拟真实配置需要的变量。
- 测试不仅要测成功路径，也要测启动时拒绝错误配置。

## 6. 验收时只测试“接口能返回”，不代表网关闭环可用

### 实际场景

下面的请求可能返回正确的错误 JSON：

```bash
curl -X POST http://localhost:8080/v1/chat/completions \
  -H "Authorization: Bearer sk-gateway-dev" \
  -d 'bad json'
```

返回 400 只能说明：

```text
网关能解析错误请求，并返回统一错误
```

它不能说明真实供应商转发成功。要验证完整链路，还必须准备一个真实或模拟的上游服务。

### 推荐的验收层次

#### 第一层：网关基础路由

```bash
curl -i http://localhost:8080/healthz
curl -i -H "Authorization: Bearer sk-gateway-dev" \
  http://localhost:8080/v1/models
```

验证健康检查、鉴权和模型列表。

#### 第二层：错误处理

```bash
curl -i -X POST http://localhost:8080/v1/chat/completions \
  -H "Authorization: Bearer wrong-key" \
  -d '{}'
```

验证 401、400、403 等错误码和 JSON 结构。

#### 第三层：模拟上游转发

用本地测试服务器模拟供应商：

```go
upstream := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
    w.Header().Set("Content-Type", "application/json")
    fmt.Fprint(w, `{"id":"test","choices":[]}`)
}))
defer upstream.Close()
```

这样不需要消耗真实 API，也能验证：

- 网关是否正确拼接上游 URL
- 是否注入供应商 API Key
- 是否转发请求体
- 是否转发响应

#### 第四层：真实供应商端到端

只有配置真实 API Key 后，才能确认：

- 供应商协议兼容
- usage 是否正确
- 非流式响应是否符合 OpenAI SDK 预期
- 流式 `[DONE]` 是否正确

### 学到的知识

验收应该分层：

```text
接口路由测试 ≠ 模拟上游测试 ≠ 真实供应商测试
```

每一层都解决不同问题，不能只运行一个 `curl` 就宣布网关完全可用。

## 8. 流式错误响应先 Close 再 Read 导致错误信息丢失

### 实际场景

供应商返回 401（API Key 无效）或 502（上游崩溃）时，网关应该把错误信息记录下来方便排查。但日志中看到的错误信息始终是空的：

```text
upstream status 401:
```

### 问题代码

```go
// openai.go / anthropic.go 中非流式请求的错误处理
resp.Body.Close()
body, _ := io.ReadAll(resp.Body)
return nil, fmt.Errorf("upstream status %d: %s", resp.StatusCode, string(body))
```

### 根因

`resp.Body.Close()` 关闭了底层 TCP 连接，之后再调用 `io.ReadAll(resp.Body)` 时 body 已被关闭，读取到的是空字节。Go 的 `http.Response.Body` 是 `io.ReadCloser`，Close 后不可再读。

### 影响

- 所有非 200 响应的错误详情丢失
- 无法区分 401（密钥错误）、403（权限不足）、429（限流）、500（服务端错误）等具体错误
- 排查问题只能靠猜测

### 修复代码

```go
// 先读后关
body, _ := io.ReadAll(resp.Body)
resp.Body.Close()
return nil, fmt.Errorf("upstream status %d: %s", resp.StatusCode, string(body))
```

### 验证方式

```bash
go build ./...
# 用无效 API Key 发送请求，检查日志中是否包含完整错误信息
```

### 学到的知识

- `io.ReadCloser` 在 Close 后不可再读，Read/Close 顺序必须正确
- 建议用 `defer resp.Body.Close()` 放在 Read 之后，避免忘记关闭
- 流式请求的 `resp.Body` 由 SSE 读取循环持有，关闭时机不同

### 相关文件和提交

- 文件：`internal/adapter/openai.go:113-117`
- 文件：`internal/adapter/anthropic.go:178-182`

## 9. fallback 方法内部调用权重轮询导致主供应商漂移

### 实际场景

配置了两个供应商，主供应商权重 100，备用供应商权重 0（仅 fallback）。主供应商失败后，fallback 却选中了主供应商自身，导致无限循环或错误跳过。

### 问题代码

```go
func (r *Router) SelectProvider(model string) *config.ProviderConfig {
    target := r.weightedSelect(route.Providers) // 计数器+1
    return r.findProviderByID(target.ProviderID)
}

func (r *Router) GetFallbackProviders(model string) []*config.ProviderConfig {
    primary := r.weightedSelect(route.Providers) // 又调用一次，计数器+1
    // 排除 primary，返回其余
}
```

### 根因

`weightedSelect` 每次调用都会递增内部计数器（原子操作），用于实现加权轮询。`GetFallbackProviders` 内部再次调用它来确定"主供应商是谁"，但此时计数器已经变化，选出的 `primary` 可能与 `SelectProvider` 选出的不一致。

```text
SelectProvider 选: provider-A (计数器: 0→1)
GetFallbackProviders 内 weightedSelect: provider-B (计数器: 1→2)
结果: fallback 排除了 provider-B，保留了 provider-A
```

### 影响

- fallback 逻辑完全失效
- 可能在主供应商失败后，fallback 仍然命中同一个主供应商
- 多供应商权重轮询分配不均衡

### 修复代码

```go
// 由调用方传入主供应商 ID，不再内部调用 weightedSelect
func (r *Router) GetFallbackProviders(model string, excludeProviderID string) []*config.ProviderConfig {
    route := r.findRoute(model)
    if route == nil || len(route.Providers) <= 1 {
        return nil
    }
    var fallbacks []*config.ProviderConfig
    for _, t := range route.Providers {
        if t.ProviderID == excludeProviderID {
            continue
        }
        if p := r.findProviderByID(t.ProviderID); p != nil {
            fallbacks = append(fallbacks, p)
        }
    }
    return fallbacks
}
```

调用方：

```go
provider := h.router.SelectProvider(req.Model)
fallbacks := h.router.GetFallbackProviders(req.Model, provider.ID)
```

### 验证方式

```bash
go test ./internal/router/ -v
# 模拟：SelectProvider 选 provider-A，GetFallbackProviders 应返回非 A 列表
```

### 学到的知识

- 有副作用的方法（如计数器递增）不应在"查询类"方法中调用
- 函数签名应明确表达意图：`GetFallbackProviders(model, excludeID)` 比 `GetFallbackProviders(model)` 更清晰
- 纯粹查询 vs 有状态变更的边界要清晰分开

### 相关文件和提交

- 文件：`internal/router/router.go:56-68`
- 文件：`internal/server/chat.go:87`

## 10. RetryableAdapter 与 handler 层 fallback 双层叠加放大延迟

### 实际场景

主供应商偶发 503，网关同时启用了重试和 fallback。一次请求的延迟远超预期，客户端超时。

### 问题代码

```go
// handler.go: adapter 层包装 RetryableAdapter（最多重试 3 次）
adp = adapter.NewRetryableAdapter(adp, h.cfg.Retry.MaxRetries, h.cfg.Retry.InitialBackoff)

// chat.go: handler 层再 fallback 到下一个供应商
for _, fb := range fallbacks {
    resp, err = h.tryNonStreamingCall(fb, r, req) // 又触发 RetryableAdapter 的 3 次重试
}
```

### 根因

两层重试机制独立运作，没有协调：

```text
层次1: RetryableAdapter 重试 3 次（指数退避: 1s + 2s + 4s = 7s）
层次2: handler fallback 到供应商 B，再次触发 RetryableAdapter 重试（又 7s）
最坏情况: 7s × 2 = 14s，加上 fallback 链中的第三个供应商 → 21s+
```

### 影响

- 请求延迟大幅放大，客户端超时
- 重试次数不可控（N 个供应商 × M 次重试）
- 上游供应商承受不必要的额外请求压力

### 修复代码

删除 `RetryableAdapter`，将重试逻辑统一到 handler 层，与 fallback 在同一层协调：

```go
// tryNonStreamingCall 内部处理重试，4xx 不重试
func (h *Handler) tryNonStreamingCall(provider *config.ProviderConfig, r *http.Request, req *model.ChatCompletionRequest) (*model.ChatCompletionResponse, error) {
    maxRetries := h.cfg.Retry.MaxRetries
    for attempt := 0; attempt <= maxRetries; attempt++ {
        if attempt > 0 {
            // 指数退避
            time.Sleep(backoff)
        }
        resp, err := adp.ChatCompletion(r.Context(), req)
        if err == nil {
            return resp, nil
        }
        if isClientError(err) {
            return nil, err // 4xx 不重试
        }
    }
    return nil, lastErr
}

// handleNonStreaming 中：重试失败后再 fallback
resp, err := h.tryNonStreamingCall(provider, r, req)
if err != nil {
    for _, fb := range fallbacks {
        resp, err = h.tryNonStreamingCall(fb, r, req) // 不再有内部 RetryableAdapter
        if err == nil { break }
    }
}
```

### 验证方式

```bash
go build ./... && go vet ./...
# 删除 internal/adapter/retry.go 后编译通过
```

### 学到的知识

- 重试和 fallback 是两种不同的容错策略，应放在同一层协调
- 不要在多个层级独立实现重试，会导致"重试放大"
- 删除 `retry.go`，将策略统一到一个地方，代码更清晰、更可控

### 相关文件和提交

- 删除：`internal/adapter/retry.go`
- 文件：`internal/server/chat.go:107-150`（新增重试 + isClientError）
- 文件：`internal/server/handler.go:36-51`（移除 RetryableAdapter 包装）

## 11. RPM=0 时令牌桶拒绝所有请求

### 实际场景

用户只想限制 QPS 而不限制 RPM，配置如下：

```yaml
rate_limit:
  sk-gateway-dev:
    qps: 100
    rpm: 0   # 期望：不限 RPM
```

结果所有请求都被拒绝。

### 问题代码

```go
rl.limits[apiKey] = &rateLimitPair{
    qpsLimiter: rate.NewLimiter(rate.Limit(cfg.QPS), cfg.QPS*2),
    rpmLimiter: rate.NewLimiter(rate.Limit(cfg.RPM)/60, cfg.RPM/60*2+1),
}
```

当 `cfg.RPM = 0` 时：`rate.Limit(0)/60 = 0`，令牌桶速率为 0，`Allow()` 永远返回 false。

### 根因

`golang.org/x/time/rate.NewLimiter(0, 0)` 创建了一个"零速率"的令牌桶，不是"无限制"的令牌桶。Go 标准库的 `rate.Limiter` 没有"不限流"模式，0 速率就是拒绝所有。

### 影响

- 配置 RPM=0 的 API Key 完全无法使用
- 用户无法实现"只限制 QPS"的配置

### 修复代码

```go
pair := &rateLimitPair{}
if cfg.QPS > 0 {
    pair.qpsLimiter = rate.NewLimiter(rate.Limit(cfg.QPS), cfg.QPS*2)
}
if cfg.RPM > 0 {
    pair.rpmLimiter = rate.NewLimiter(rate.Limit(cfg.RPM)/60, cfg.RPM/60*2+1)
}

// Allow 中：nil 限制器视为不限流
func (rl *RateLimiter) Allow(apiKey string) bool {
    if pair.qpsLimiter != nil && !pair.qpsLimiter.Allow() {
        return false
    }
    if pair.rpmLimiter != nil && !pair.rpmLimiter.Allow() {
        return false
    }
    return true
}
```

### 验证方式

```bash
go test ./internal/middleware/ -v -run RateLimit
# 测试 RPM=0 时请求正常通过
```

### 学到的知识

- 零值不一定代表"无限制"，需要查阅库的文档确认语义
- 用 nil 指针区分"未配置"和"配置为 0"两种状态
- 配置验证时，应明确 0 代表"禁用该维度"

## 12. 重试不区分 4xx 和 5xx 导致无效重试

### 实际场景

用户使用已过期的 API Key，供应商返回 401。网关仍然重试 3 次，每次重试都返回相同的 401，白白浪费了 6 秒等待时间。

### 问题代码

```go
// 对所有错误一视同仁，全部重试
for attempt := 0; attempt <= maxRetries; attempt++ {
    resp, err := adp.ChatCompletion(r.Context(), req)
    if err == nil {
        return resp, nil
    }
    // 继续重试，不管是什么错误
}
```

### 根因

HTTP 4xx 状态码表示客户端错误（请求本身有问题），无论重试多少次结果都一样。只有 5xx（服务端错误）和网络超时等临时性错误才值得重试。

| 状态码 | 含义 | 重试？ |
|--------|------|--------|
| 400 | 请求格式错误 | 否 |
| 401 | 认证失败 | 否 |
| 403 | 权限不足 | 否 |
| 429 | 限流 | 看情况（应退避） |
| 500 | 服务端内部错误 | 是 |
| 502 | 网关错误 | 是 |
| 503 | 服务不可用 | 是 |

### 影响

- 4xx 错误重试浪费时间和上游配额
- 延迟增加，用户体验变差
- 对限流（429）无脑重试可能加剧限流

### 修复代码

```go
func isClientError(err error) bool {
    errStr := err.Error()
    for code := 400; code < 500; code++ {
        if strings.HasPrefix(errStr, fmt.Sprintf("upstream status %d", code)) {
            return true
        }
    }
    return false
}

// 在重试循环中
if isClientError(err) {
    return nil, err // 4xx 不重试，直接返回
}
```

### 验证方式

```bash
go build ./...
# 用无效 API Key 测试：应只请求 1 次，不重试
```

### 学到的知识

- 重试策略必须有"不可重试错误"的白名单或黑名单
- 4xx = 客户端错误 = 不可重试；5xx = 服务端错误 = 可重试
- 更好的做法：在 adapter 层返回结构化错误（含状态码），避免字符串匹配

### 相关文件和提交

- 文件：`internal/server/chat.go:152-161`

## 21. DeepSeek Anthropic 端点返回 thinking 内容块，适配器结构体缺字段导致解析丢失

### 实际场景

DeepSeek 的 Anthropic 兼容端点返回的内容块中，包含 `thinking` 类型：

```json
{
  "content": [
    {"type": "thinking", "thinking": "The user wants...", "signature": "..."},
    {"type": "text", "text": "Hello"}
  ]
}
```

流式 SSE 事件中也有 `thinking_delta` 类型：

```json
{"type": "content_block_delta", "delta": {"type": "thinking_delta", "thinking": "The user..."}}
```

但通过网关后，思考内容完全丢失，日志中也没有任何报错。

### 问题代码

```go
// anthropicContent 只有 text 字段，缺少 thinking 字段
type anthropicContent struct {
    Type string `json:"type"`
    Text string `json:"text"`
}

// anthropicDelta 同样只有 text 字段
type anthropicDelta struct {
    Type string `json:"type"`
    Text string `json:"text"`
}
```

### 根因

DeepSeek V4 默认开启思考模式（reasoning），在 Anthropic 格式中体现为 `type: "thinking"` 的内容块和 `type: "thinking_delta"` 的增量事件。适配器的结构体只定义了 `text` 字段，JSON 反序列化时 `thinking` 字段被丢弃。

同时 `model.ChatMessage` 和 `model.Delta` 也没有 `ReasoningContent` 字段，即使适配器层解析了思考内容也没有地方存放。

### 影响

- 思考内容完全丢失，用户看不到推理过程
- 思考 Token 的消耗无法统计（网关侧计费不准确）
- 不影响最终答案内容（`text` 类型块正常透传）

### 修复代码

```go
// model.go: 新增 ReasoningContent 字段
type ChatMessage struct {
    // ...
    ReasoningContent string `json:"reasoning_content,omitempty"`
}

type Delta struct {
    // ...
    ReasoningContent string `json:"reasoning_content,omitempty"`
}

// anthropic.go: 结构体新增 Thinking 字段
type anthropicContent struct {
    Type     string `json:"type"`
    Text     string `json:"text"`
    Thinking string `json:"thinking"`
}

type anthropicDelta struct {
    Type     string `json:"type"`
    Text     string `json:"text"`
    Thinking string `json:"thinking"`
}

// convertResponse: 提取 thinking 类型
switch c.Type {
case "text":
    content += c.Text
case "thinking":
    reasoning += c.Thinking
}

// readStream: 处理 thinking_delta 事件
case "thinking_delta":
    ch <- StreamEvent{Chunk: &model.StreamChunk{
        Choices: []model.StreamChoice{{
            Delta: model.Delta{ReasoningContent: event.Delta.Thinking},
        }},
    }}
```

### 验证方式

```bash
# 流式请求 DeepSeek V4，检查 reasoning_content 是否出现在 SSE 事件中
# 非流式请求，检查响应 JSON 中是否有 reasoning_content 字段
```

### 学到的知识

- 第三方供应商的"兼容格式"往往有扩展字段，需要在适配器层做适配
- 字段名映射是适配器开发的核心工作：Anthropic 的 `thinking` → OpenAI 的 `reasoning_content`
- 用 `omitempty` 标签确保没有思考功能的模型不受影响
- 新增可选字段时，所有下游结构体（ChatMessage、Delta、StreamChunk）都要同步检查

### 相关文件和提交

- 文件：`internal/model/model.go`
- 文件：`internal/adapter/anthropic.go`

## 22. StreamChunk 缺少 Usage 字段导致流式 Token 用量丢失

### 实际场景

Anthropic SSE 协议的 `message_delta` 事件携带 Token 用量：

```json
{"type": "message_delta", "usage": {"input_tokens": 88, "output_tokens": 36}}
```

适配器的 `readStream` 虽然解析了 `event.Usage`，但 `StreamChunk` 结构体没有 `Usage` 字段，无法写入。导致流式请求的最后一个 chunk 中缺少 usage 信息。

### 问题代码

```go
// model.go: StreamChunk 没有 Usage 字段
type StreamChunk struct {
    ID                string         `json:"id"`
    Object            string         `json:"object"`
    Created           int64          `json:"created"`
    Model             string         `json:"model"`
    Choices           []StreamChoice `json:"choices"`
    SystemFingerprint string         `json:"system_fingerprint,omitempty"`
    // 缺少 Usage
}

// anthropic.go: 解析了 Usage 但没地方放
case "message_delta":
    if event.Usage != nil {
        ch <- StreamEvent{Chunk: &model.StreamChunk{
            // Usage 被丢弃
        }}
    }
```

### 根因

`StreamChunk` 最初设计时没有考虑流式 Token 用量。OpenAI 和 Anthropic 都在流式最后一个 chunk 中返回 usage，这是一个标准行为。同时 `message_delta` 事件中即使 `event.Usage != nil`，也只发了 finish_reason，没有携带 usage。

### 影响

- 流式请求完成后，客户端无法获取 Token 用量
- 网关自身的 Token 统计（P1 任务）在流式模式下完全不可用
- 与 OpenAI 流式协议不一致（OpenAI 在最后 chunk 返回 usage）

### 修复代码

```go
// model.go: 新增 Usage 字段
type StreamChunk struct {
    // ...
    Usage *Usage `json:"usage,omitempty"`
}

// anthropic.go: 填充 Usage
case "message_delta":
    finishReason := "stop"
    var usage *model.Usage
    if event.Usage != nil {
        usage = &model.Usage{
            PromptTokens:     event.Usage.InputTokens,
            CompletionTokens: event.Usage.OutputTokens,
            TotalTokens:      event.Usage.InputTokens + event.Usage.OutputTokens,
        }
    }
    ch <- StreamEvent{Chunk: &model.StreamChunk{
        Choices: []model.StreamChoice{{
            FinishReason: &finishReason,
        }},
        Usage: usage,
    }}
```

### 验证方式

```bash
# 流式请求，检查最后一个 SSE chunk 是否包含 usage 字段
# 预期: {"usage":{"prompt_tokens":88,"completion_tokens":36,"total_tokens":124}}
```

### 学到的知识

- 结构体设计要考虑上下游协议的全貌，不只是"当前能用"
- OpenAI 和 Anthropic 都在流式最后 chunk 返回 usage，这是事实标准
- `omitempty` 对于指针类型字段，nil 时不输出，不影响没有 usage 的供应商
- 非流式请求的 usage 在 `ChatCompletionResponse.Usage` 中，流式在 `StreamChunk.Usage` 中，两个都要维护
