## 一、P0：验证（目标①收尾）

### 1.1 验证过程

**环境准备**：拿到 DeepSeek API Key `sk-2200ae...`，在 `config.yaml` 中配置了两个 provider：
- `deepseek-anthropic`（type: anthropic, base_url: `https://api.deepseek.com/anthropic`）
- 使用 DeepSeek V4 Flash 和 V4 Pro 模型

**第一步：OpenAI 格式非流式**

```bash
curl -X POST http://localhost:8080/v1/chat/completions \
  -H "Authorization: Bearer sk-gateway-dev" \
  -H "Content-Type: application/json" \
  -d '{"model":"deepseek-v4-flash","messages":[{"role":"user","content":"你好"}],"stream":false}'
```

→ 请求成功返回，验证了 OpenAI 格式适配器正常工作。

**第二步：OpenAI 格式流式**

```bash
curl -X POST http://localhost:8080/v1/chat/completions \
  -H "Authorization: Bearer sk-gateway-dev" \
  -H "Content-Type: application/json" \
  -d '{"model":"deepseek-v4-flash","messages":[{"role":"user","content":"你好"}],"stream":true}'
```

→ 报错 `"streaming not supported"`。排查发现：日志中间件包装了 `http.ResponseWriter`，但 `responseWriter` 结构体没有实现 `http.Flusher` 接口，导致 `handler.go` 中的类型断言 `w.(http.Flusher)` 失败。

**修复**：在 `middleware/logger.go` 的 `responseWriter` 结构体添加 `Flush()` 方法，委托给底层 `ResponseWriter`。修复后流式请求正常返回 SSE 事件流。

**第三步：Anthropic 格式非流式**

修改配置将 DeepSeek 路由到 `deepseek-anthropic` provider（type: anthropic），请求同样参数。

→ 返回正常，但发现 `reasoning_content`（思考内容）为空。排查发现：Anthropic 适配器的 `anthropicContent` 结构体缺少 `Thinking` 字段，DeepSeek 返回的 `type: "thinking"` 内容块被丢弃。

**修复**：在 `anthropicContent`、`anthropicDelta` 添加 `Thinking` 字段，在 `ChatMessage`、`Delta` 添加 `ReasoningContent` 字段，在 `convertResponse` 和 `readStream` 中提取思考内容。修复后思考内容完整保留。

**第四步：Anthropic 格式流式**

→ 流式正常，但最后一个 chunk 的 `usage` 为 null。排查发现：`StreamChunk` 结构体缺少 `Usage` 字段，适配器处理 `message_delta` 事件时未提取用量信息。

**修复**：为 `StreamChunk` 添加 `Usage` 字段，在 `readStream` 中处理 `message_delta` 事件时填充 `event.Usage` 到 chunk。修复后流式最后一个 chunk 正确携带 Token 用量。

## 二、P1：部署 + 可观测性（目标⑤）

### 2.1 完成过程

**任务 8：Dockerfile（多阶段构建）**

目标：最终镜像 < 20MB。

过程：
1. 搜索 Go Docker 最佳实践，确定多阶段构建方案：`golang:alpine` 编译 + `scratch` 空镜像运行
2. 先复制 `go.mod` / `go.sum` 再 `go mod download`，利用 Docker 缓存层，改代码不用重新下载依赖
3. 编译时 `CGO_ENABLED=0` 禁用 CGO 生成纯静态二进制，`-ldflags="-s -w"` 去除调试信息减小体积
4. 用 `scratch` 作为运行镜像（完全空白的镜像，0 字节），从编译阶段复制 CA 证书和二进制
5. 构建验证：`docker build -t go-gateway .`，最终镜像 **10.6MB**，满足目标

遇到的问题：
- 容器内 `go mod download` 访问 `proxy.golang.org` 超时（国内网络问题）
- 解决：在 Dockerfile 中加 `RUN go env -w GOPROXY=https://goproxy.cn,direct`

**任务 9：docker-compose.yml（三服务编排）**

目标：一键启动 gateway + prometheus + grafana。

过程：
1. 配置 gateway 服务：`build: .` 本地构建，挂载 `config.yaml` 和 `logs` 目录
2. 配置 prometheus 服务：使用官方镜像 `prom/prometheus:latest`，挂载 `prometheus.yml` 配置
3. 配置 grafana 服务：使用官方镜像 `grafana/grafana:latest`，设置默认账号 admin/admin
4. 添加 `prometheus_data` 和 `grafana_data` 命名卷持久化数据
5. 创建 `prometheus.yml`，配置 `scrape_interval: 15s`，target 指向 `gateway:8080`
6. 创建 Grafana provisioning 配置：datasource 自动连接 Prometheus，dashboard 自动加载
7. 验证：`docker-compose up -d`，三个服务全部启动成功

遇到的问题：
- 容器启动时提示环境变量 `OPENAI_API_KEY` 未设置
- 解决：在 `docker-compose.yml` 中为 gateway 服务添加 `environment` 配置

**任务 10：健康检查增强**

目标：`/healthz` 不仅返回自身状态，还要检查上游供应商连通性。

过程：
1. 在 Adapter 接口中新增 `HealthCheck() error` 方法
2. OpenAI 适配器实现：GET `/v1/models`，5 秒超时，500+ 视为不健康
3. Anthropic 适配器实现：GET `/v1/messages`，5 秒超时，500+ 视为不健康
4. 修改 `handler.go` 的 `HealthCheck` 方法：遍历所有 provider，逐个检查连通性
5. 任一供应商不健康返回 `"degraded"` + HTTP 503，全部健康返回 `"ok"` + 200
6. 同时更新 `gateway_upstream_health` Prometheus 指标

**任务 11-12：Prometheus 指标 + /metrics 端点**

目标：定义 5 个业务指标，暴露 `/metrics` 端点。

过程：
1. `go get github.com/prometheus/client_golang` 安装依赖
2. 创建 `internal/metrics/metrics.go`，定义 5 个指标：
   - `gateway_requests_total`（CounterVec）：请求总数，按 model/status_code/provider 分组
   - `gateway_request_duration_seconds`（HistogramVec）：延迟分布，bucket 设为 0.1/0.5/1/2/5/10/30/60/120 秒
   - `gateway_errors_total`（CounterVec）：错误数，按 error_type 分组
   - `gateway_tokens_consumed_total`（CounterVec）：Token 消耗，按 token_type 分组
   - `gateway_upstream_health`（GaugeVec）：上游健康，1=UP, 0=DOWN
3. 在 `init()` 中 `prometheus.MustRegister()` 注册所有指标
4. 暴露 `Handler()` 函数返回 `promhttp.Handler()`
5. 在 `handler.go` 中注册路由：`mux.Handle("/metrics", metrics.Handler())`

**任务 13：Grafana Dashboard**

目标：创建 7 面板可视化仪表盘。

过程：
1. 创建 `grafana/dashboards/go-gateway.json`，格式为 Grafana Dashboard JSON
2. 7 个面板：请求速率（折线图）、延迟 P50/P95/P99（折线图）、错误率（折线图）、Token 消耗速率（折线图）、上游健康（指示灯）、总请求数（大数字）、Token 总消耗（大数字）
3. 配置 `dashboard.yml` 自动加载
4. 遇到问题：文件 provisioning 在 Grafana v13 中不生效，Dashboard 未自动加载
5. 通过 API 手动导入：`POST /api/dashboards/db`，Dashboard 成功创建并持久化

**任务 14：Token 用量统计**

目标：记录每个请求的 Token 消耗，按 prompt/completion 分别统计。

过程：
1. 在 `handleNonStreaming` 中：请求完成后，从 `resp.Usage` 提取 `PromptTokens` 和 `CompletionTokens`，累加到 `gateway_tokens_consumed_total`
2. 在 `handleStreaming` 中：遍历 SSE 事件时收集最后一个 chunk 的 `Usage`，流结束后累加到指标
3. 同时在请求成功时记录 `gateway_requests_total` 和 `gateway_request_duration_seconds`
4. 在请求失败时记录 `gateway_errors_total`（按 error_type 区分：no_provider / no_adapter / upstream_error / stream_error 等）
5. 验证：发送 4 次请求后，`curl localhost:8080/metrics | findstr gateway_` 确认指标数据正确
