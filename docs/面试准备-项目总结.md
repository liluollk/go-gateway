# 面试准备：Go 语言 AI 模型网关项目

> 从零用 Go 构建企业级 AI 模型统一接入网关，覆盖架构设计、中间件、适配器模式、限流、重试、测试全链路。

---

## 一、项目概述（一句话介绍）

> 用 Go 实现了一个 AI 模型网关，统一接入 OpenAI、Anthropic 等多个大模型供应商，提供鉴权、路由、限流、协议转换和日志能力。业务方只需改 `base_url`，代码零改动即可接入。

**核心价值：**

| 问题 | 网关解决的 |
|------|-----------|
| 多个供应商的 API 格式不一致 | Adapter 模式统一协议，OpenAI ↔ Anthropic 自动转换 |
| API Key 散落在各业务代码 | 网关统一管理 Key，业务方只拿网关 Key |
| 供应商挂了影响业务 | 自动 fallback 到备用供应商，指数退避重试 |
| 无法控制成本 | 按 API Key 独立限流，QPS + RPM 双维度 |

---

## 二、系统架构

```
请求 → RequestID → Auth → RateLimit → Logger → Router → Adapter → 上游 API
```

| 中间件 | 职责 |
|--------|------|
| **RequestID** | 注入 `X-Trace-Id`，全链路追踪 |
| **Auth** | Bearer Token 鉴权 + 模型白名单 |
| **RateLimit** | 令牌桶算法，QPS + RPM 双维度限流 |
| **Logger** | JSON Lines 格式日志，按天轮转 |
| **Router** | 权重轮询选择供应商，失败自动 fallback |
| **Adapter** | 隔离供应商差异，自动转换 OpenAI ↔ Anthropic 格式 |

### 面试时可以说

> "我采用了**中间件责任链模式**（和 Gin 的中间件一样），每个中间件只做一件事。Auth 验证完往 context 里塞模型列表，RateLimit 从 context 里拿 API Key 做限流。解耦得非常干净，加新中间件不需要改任何现有代码。"

### Phase 2：多供应商工程化（Adapter 模式 + 路由 + 限流 + 重试）

**这是面试重点，面试官最爱问设计模式。**

#### 2.1 Adapter 模式（核心设计）

```go
type Adapter interface {
    ChatCompletion(ctx, req) (*ChatCompletionResponse, error)
    ChatCompletionStream(ctx, req) (<-chan StreamEvent, error)
    GetProviderType() string
}
```

**为什么用 Adapter 模式？**

- 不同供应商的 API 格式完全不同（OpenAI 用 messages 数组，Anthropic 用 system prompt 单独字段 + messages 数组）
- 通过 Adapter 把差异关在实现里，上层统一用 OpenAI 格式
- 加新供应商不改代码，只改 YAML 配置

**DeepSeek 为例：** 只需在 `config.yaml` 加三行，`type: openai` 自动复用 `OpenAIAdapter`，因为 DeepSeek 兼容 OpenAI 格式。

```yaml
providers:
  - id: deepseek-main
    type: openai                    # 复用 OpenAIAdapter
    base_url: https://api.deepseek.com
    api_key: ${DEEPSEEK_API_KEY}
```

**面试可以说：** "我用了策略模式的一个变体——Adapter 模式。所有供应商实现同一个 `Adapter` 接口，`initAdapters()` 在启动时根据配置的 `type` 字段（`openai`/`anthropic`）动态创建适配器。加新供应商不需要改代码，和 Spring 的 `@ConditionalOnProperty` 一个道理。"

#### 2.2 Anthropic 格式转换（最难的部分）

OpenAI 和 Anthropic 的请求格式差异：

| 维度 | OpenAI | Anthropic |
|------|--------|-----------|
| 请求体结构 | `messages` 数组，system 也是一条消息 | `system` 是独立字段，`messages` 数组不含 system |
| 角色命名 | `"assistant"` | `"assistant"` |
| 流式响应 | `data: {...}\n\n` | `event: content_block_delta\ndata: {...}\n\n` |
| Token 用量 | 在非流式响应顶层 | 在流式的 `message_delta` 事件中 |
| 请求头 | `Authorization: Bearer xxx` | `x-api-key: xxx` + `anthropic-version: 2023-06-01` |

**流式响应处理的坑：** OpenAI 的 SSE 是 `data: {...}\n\n`，一行搞定。Anthropic 是 `event: xxx\ndata: {...}\n\n`，双行结构。解析时如果漏掉 `event:` 行，就会丢事件类型，导致 `message_delta` 里的 usage 信息丢失。

**面试可以说：** "最复杂的是 Anthropic 的流式格式转换。Anthropic 的 SSE 有 `event:` + `data:` 双行结构，必须用 `bufio.Scanner` 逐行解析，按 `event:` 行记录当前事件类型，在 `data:` 行拿到内容后根据事件类型做不同处理。我写了 80 行的 `readStream` 方法专门处理这个。"

#### 2.3 路由 + Fallback

```go
// 权重轮询：用 atomic.Uint64 全局递增计数器，取模选供应商
func (r *Router) SelectProvider(model string) *ProviderConfig {
    // 1. 找到匹配的 route
    // 2. 按权重轮询选供应商
    // 3. 返回 ProviderConfig
}

// Fallback：主供应商失败后，依次尝试其他供应商
func (r *Router) GetFallbackProviders(model, excludeID string) []*ProviderConfig { ... }
```

**踩过的坑：** fallback 方法内部调用权重轮询导致主供应商漂移——每次 fallback 重新调用 `SelectProvider` 会随机选到不同供应商。修复方式是 fallback 用独立的 `GetFallbackProviders` 方法，排除主供应商后按顺序返回。

**面试可以说：** "我用 `atomic.Uint64` 做全局递增计数器实现权重轮询，无锁高性能。fallback 链是写死的，不在 fallback 中再次轮询，避免主供应商漂移。"

#### 2.4 限流：令牌桶算法

```go
// QPS 桶：每秒 rate.Limit(qps) 个令牌，burst = qps*2
// RPM 桶：每分钟 rate.Limit(rpm)/60 个令牌
// 任一维度触发限制 → 返回 429
```

**面试可以说：** "我用 `golang.org/x/time/rate` 的标准库实现令牌桶。关键是 burst 设置——我设成 `QPS*2`，允许瞬间突发流量。比如 QPS=100，burst=200，前 200 个请求瞬间通过，之后严格按 100/s 限速。这比简单的固定窗口计数器更平滑，不会出现边界突发。"

#### 2.5 重试策略

```go
// 指数退避：1s, 2s, 4s, ... 最大 30s
// 4xx 不重试（客户端错误，重试无意义）
// 5xx 和网络错误重试
// 非流式请求支持 fallback
// 流式请求不支持 fallback（已开始发送数据，无法切换供应商）
```

**面试可以说：** "重试策略的核心是区分 4xx 和 5xx。我定义了 `UpstreamError` 结构体，用 `errors.As` 做类型断言判断是否为客户端错误，而不是字符串匹配。这样即使错误格式变了也不会误判。"

## 四、踩过的坑（面试时展示解决问题的能力）

| # | 问题 | 根因 | 修复 |
|---|------|------|------|
| 1 | 日志轮转时死锁 | `rotate()` 和 `Write()` 两次加锁 | 拆分 `rotateLocked()` 内部方法，统一锁外调用一次 |
| 2 | 流式响应内存泄漏 | 缓冲整个响应体再解析 | 改为 `bufio.Scanner` 逐行读取 |
| 3 | 上游错误原样返回 | 暴露供应商内部错误信息 | 包装为统一错误码，不泄露上游细节 |
| 4 | fallback 内部调用轮询 | fallback 重新走 `SelectProvider` | 独立的 `GetFallbackProviders`，排除主供应商 |
| 5 | 重试 + fallback 双层叠加 | handler 层和 adapter 层都重试 | 只在 handler 层统一重试 + fallback |
| 6 | RPM=0 时拒绝所有请求 | 令牌桶速率为 0 时 `Allow()` 返回 false | 增加判断：RPM=0 时不创建令牌桶，不限流 |
| 7 | 用字符串匹配判断 4xx | `strings.HasPrefix(errStr, "upstream status 4xx")` | 定义 `UpstreamError` 结构体，用 `errors.As` 类型断言 |
| 8 | Anthropic 流式 usage 丢失 | `message_delta` 事件被忽略 | 解析 `event:` 行，识别 `message_delta` 事件并提取 usage |

## 五、面试时你可能被问到的问题

### Q1: 为什么不用 Nginx/Envoy 做网关？

**答：** Nginx 只能做 HTTP 反向代理，它不理解 AI 模型的协议语义。我需要：
- 不同供应商的请求/响应格式转换（OpenAI ↔ Anthropic）
- 按 API Key 的模型白名单鉴权
- 非流式请求的 fallback（供应商 A 失败→自动切供应商 B）
- 流式请求的 SSE 逐块转发

这些是应用层逻辑，Nginx 做不到。

### Q2: 怎么保证不丢请求？

**答：** 两层保障：
1. **优雅关闭：** 收到 SIGTERM 后不再接受新请求，等现有请求处理完再退出（最多 30s）
2. **非流式请求 fallback：** 主供应商失败自动切备用供应商，配合指数退避重试

### Q3: 怎么加新供应商？

**答：** 只改 `config.yaml`，不改代码。`type: openai` 的供应商自动复用 `OpenAIAdapter`（DeepSeek、vLLM、Ollama 都是这个类型）。`type: anthropic` 走 `AnthropicAdapter`。如果未来有新的协议类型（如 Google Gemini），只需实现 `Adapter` 接口，在 `initAdapters()` 的 switch 里加一个 case。

### Q4: 你的限流是怎么实现的？

**答：** 令牌桶算法，Go 标准库 `golang.org/x/time/rate`。每个 API Key 独立限流，支持 QPS 和 RPM 双维度。burst 设成 `QPS*2`，允许瞬间突发。未配置的 Key 不限流。

### Q5: 4xx 和 5xx 错误你怎么区分？

**答：** 我定义了 `UpstreamError` 结构体，包含 `StatusCode int` 字段。用 `errors.As` 做类型断言，调用 `IsClientError()` 方法判断。4xx 不重试（客户端错误，重试无意义），5xx 和网络错误进行指数退避重试。

### Q6: 项目里你最自豪的设计是什么？

**答：** Adapter 模式。**加新供应商只改 YAML，不改代码。** 这是整个项目的核心价值——把"变化"关在配置里。`initAdapters()` 在启动时根据 `type` 字段动态创建适配器，之后请求来了直接从 map 里取。这就像 Spring 的依赖注入，只是我用 Go 的 map 和 switch 自己实现了。

### Q7: 这个项目有什么不足？

**答：** 诚实地说三点：
1. **没有配置热加载**——改配置要重启（但重启只要 1 秒，优雅关闭保证不丢请求）
2. **Anthropic 流式未经过真实 API 验证**——只在 mock server 上测过
3. **没有 Prometheus 指标**——上线后需要加监控
